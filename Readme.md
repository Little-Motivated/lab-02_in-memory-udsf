# In memory UDSF
В рамках этой лабораторной предлагается реализовать аналог сервиса UDSF (Unstructured Data Storage Funstion) на языке c++. Сервис должен запустить сервер, который будет обрабатывать запросы по протоколу HTTP. Для реализации http можно использовать любой фреймворк, например seastar или cpp-httplib. Данные можно сохранять в оперативной памяти.

В UDSF данные хранятся в формате набора записей. Запись определяется 3-мя параметрами RealmId, StorageID и RecordId. Запись состоит из meta данных (любой корректный json) и нескольких блоков данных (блоки могут быть разных типов). Для работы с конкретным блоком также указывается его BlockId.

Реализовать опрерации по аналогии 3GPP TS 29.598:
 - GetRecord - получение всей записи
 - CreateOrModifyRecord - создание записи
 - DeleteRecord - удаление записи
 - GetBlockList - получение списка блоков для записи
 - GetBlock - получение конкретного блока
 - CreateOrModifyBlock - создание или модификация блока
 - DeleteBlock - удаление блока

Для операций GetRecord возвращать данные в том же формате, что и в запросе CreateOrModifyRecord. Для GetBlockList возвращать тоже же, что и в запросе GetRecord, но без meta данных.

Для каждой опреации указываются Realm и Storage. Они должны создаваться динамически при запросе на создание record, но создание блока возможно только в существующем record. Для GetBlock нужно заполнить Content-Type согласно типу данных блока.

Пример реализации на python можно посмотреть в example.py

## Проверка

Для запуска тестов:
```
python test.py --cmd 'команда запуска решения' --addr 'адрес http сервера в формате addr:port'
```

Завсимости указаны в requirements.txt

## Дополнительные задачи

### Задача со звездочкой 1:
Сервисом может пользоваться несколько клиентов. Для создания защиты от одновременного изменения одного и того же ресурса необходимо реализовать механизм контроля параллельных изменений. Для этого предлогается добавить следующие хедеры:
 - Для GET запроса:
    - ETag - согласно RFC 7232 (сильная валидация), задавать новое уникальное значение на каждое изменение записи
 - Для PUT и DELETE запросов:
    - If-Match - согласно RFC 7232 (сильная валидация), совпадение текущего etag этой записи или запись существует для "*"
    - If-None-Match - согласно RFC 7232 (сильная валидация), не совпадение текущего etag этой записи или запись не существует для "*"

### Задача со звездочокй 2:
Для операции GetBlockList сделать ответ в формате `multipart/mixed`. Данный формат позволяет вернуть ответ из множества объектов разных форматов. Про структуру можно почитать в RFC 2046. Объекты отделяются строкой delimeter и для каждого объекта можно указать набор загаловков относящихся к этому объекту. Для каждого блока нужно добавить header `Content-Id` со значением BlockId и `Content-Type` с соответствующим значением, после чего идет значение блока. Обратите винмание: при кодировании нужно выбрать разделитель - строку, которая не встречается в данных.

пвример для разделителя `simple boundary`
```
--simple boundary
Content-Id: block1
Content-type: application/json

{"key":"value"}
--simple boundary
Content-Id: block2
Content-type: text/plain

This is explicitly typed plain US-ASCII text.
It DOES end with a linebreak.

--simple boundary--
```

### Задача со звездочокй 3:
Добавить сохранение данных на диск, чтобы перезапуск приложения не приводил к потере данных. Формат и способ хранения данных студент выбирает самостоятельно.

### Задача со звездочокй 4:
Добавить многопоточность. Обрабатывать запросы от клинета в 2-х потоках, а данные хранить в 2-х других потоках. Номер потока на котором хранится запись считать как остаток от деления на 2 для значения хеша от ключа. Алгоритм хеширования студент определяет самостоятельно.
